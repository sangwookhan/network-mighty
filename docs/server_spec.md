# 웹 마이티 — 서버 운용 및 접속 스펙 (v0.1 초안)

원작의 TCP 프로토콜(`re/02_network_protocol.md`)은 따르지 않는다. 원작은 모든 클라이언트에 덱 전체를 보내는 구조라서 웹 버전에는 맞지 않는다. 원작 문서는 메시지 종류와 게임 흐름을 참고하는 용도로만 쓴다.

## 1. 결정 사항

| 항목 | 결정 |
|---|---|
| 대상 | 아는 사람끼리 소규모 (동시에 방 몇 개 수준) |
| 입장 | 닉네임만 입력. 가입·로그인 없음 |
| 방 찾기 | 로비의 방 목록에서 골라 입장 (방 링크 공유도 지원) |
| 인원 부족 | **봇으로 빈자리를 채운다 (필수)** |
| 판정 | 서버가 규칙 판정과 진행을 모두 맡는다. 클라이언트는 화면 표시와 입력만 한다 |
| 게임 중 입장 | 관전자로 들어와서, 원하면 봇 자리를 골라 넘겨받는다 |
| 차례 제한 시간 | 방장이 방 설정에서 정한다 |
| 다음 판 시작 | 원작 정책을 따른다: 정산 화면에서 각자 [계속]/[그만] 선택 (§4) |
| 봇 수준 | 단순 봇으로 시작해서 점차 개선한다 |
| 전적 저장 | 하지 않는다 (서버 메모리에만 둠) |
| 서버 위치 | 미정 → §6 추천안 참고 |

## 2. 전체 구조

```
브라우저 ──HTTPS──▶ Node 서버 1개 (프로세스 1개)
         ◀─WebSocket─▶  ├ 정적 파일 제공 (웹 클라이언트)
                        ├ 로비: 접속자, 방 목록
                        ├ 방마다 게임 진행기 (서버가 판정)
                        ├ 규칙 엔진 (TypeScript, 클라이언트와 공유)
                        └ 봇 (같은 프로세스 안에서 실행)
```

- 상태는 서버 메모리에만 둔다. 서버를 재시작하면 방이 사라진다.
- 전적이나 점수는 파일·DB에 저장하지 않는다. 누적 점수는 방이 살아 있는 동안만 유지된다.
- DB, Redis, 별도 봇 서버는 두지 않는다.
- 규칙 엔진은 서버와 클라이언트가 같은 코드를 쓴다. 서버는 판정에 쓰고, 클라이언트는 낼 수 있는 카드를 미리 표시하는 데만 쓴다.

## 3. 접속과 신원

1. 처음 들어오면 닉네임을 입력한다. 서버가 무작위 **세션 토큰**을 발급하고, 브라우저는 이 토큰을 localStorage에 저장한다.
2. 다시 접속하면 토큰으로 같은 사람임을 확인한다. 게임 중이었다면 원래 자리로 돌아간다.
3. 같은 시각에 같은 닉네임은 쓸 수 없다. 이미 쓰는 닉네임이면 다른 닉네임을 요청한다.
4. 토큰은 재접속할 때 자리를 되찾는 용도로만 쓴다. 영구 계정이나 전적은 없다.

## 4. 로비와 방

**로비 화면**
- 방 목록을 보여준다: 방 이름, 규칙 프리셋, 사람 수와 봇 수(예: 사람 2 + 봇 3 / 5), 관전자 수, 상태(대기 중/게임 중).
- 접속자 목록과 로비 채팅이 있다.
- [방 만들기] 버튼이 있다.

**방 만들기**
- 방 이름, 규칙 프리셋(12종 중 선택, 세부 옵션은 대기실에서 수정), 차례 제한 시간을 정한다. 비밀번호는 선택이다.
- 만든 사람이 방장이 된다.

**방 입장**
- 대기 중인 방에 빈자리나 봇 자리가 있으면 앉는다. 봇 자리에 앉으면 그 봇은 빠진다.
- 게임 중인 방에 들어오면 **관전자**가 된다.
  - 관전자는 공개된 정보만 본다: 테이블에 나온 카드, 공약, 프렌드 조건, 점수. 남의 패는 보지 않는다.
  - 관전자는 채팅을 할 수 있다.
  - 관전자가 봇 자리 하나를 골라 [이 자리 넘겨받기]를 누르면 그 자리에 앉는다. 다음 결정부터 직접 조작하고, 그 자리의 패가 보이기 시작한다.
  - 사람이 앉은 자리는 넘겨받을 수 없다. 연결이 끊겨 봇이 임시로 대신 치는 자리도 원래 주인이 돌아올 수 있도록 일정 시간 동안 막아 둔다 (§5).
  - 자리를 넘겨받은 사람은 그 자리의 누적 점수를 이어받는다.
- 대기 중인 방에 빈자리가 없을 때도 관전자로 들어간다.
- 방 링크(`/room/<id>`)로 들어와도 같은 절차를 거친다.

**대기실 (방 안, 게임 시작 전)**
- 자리 목록을 보여준다. 각 자리는 사람, 봇, 빈자리 중 하나다.
- 방장이 할 수 있는 일:
  - 규칙 변경
  - 차례 제한 시간 변경
  - 빈자리에 봇 추가, 봇 빼기
  - 플레이어 내보내기
  - [시작]
- **[시작]을 누르면 남은 빈자리가 모두 봇으로 채워진다.** 사람 1명이어도 봇 4명과 5마를 칠 수 있다.

**판이 끝났을 때 (원작 정책)**
- 원작은 정산이 끝나면 점수판을 띄우고 각 플레이어에게 계속할지 묻는다. 누군가 그만두면 게임 전체가 끝난다 (`re/03_game_flow_and_ai.md` §2.3의 S4, `OnEnd`).
- 웹 버전은 이렇게 옮긴다:
  - 정산 화면에서 사람마다 [계속] 또는 [그만]을 고른다. 봇은 항상 [계속]이다.
  - 모든 사람이 [계속]을 고르면 다음 판을 시작한다. 선은 원작 규칙대로 주공이 잡는다. "전판 프렌드가 딜러" 규칙이 켜져 있으면 프렌드가 잡는다.
  - [그만]을 고른 사람은 게임 전체를 끝내지 않고 **자리에서 일어난다**. 그 자리는 봇이 맡고, 그 사람은 관전자가 되거나 로비로 나간다. 원작과 달리 한 사람 때문에 다른 사람들의 게임이 끝나지 않게 한다.
  - 정산 화면에도 차례 제한 시간을 적용한다. 시간 안에 고르지 않으면 [계속]으로 본다.
  - 방에 사람이 한 명도 남지 않으면 방을 닫는다.

## 5. 봇 (필수 기능)

**봇이 들어가는 경우**
1. 게임을 시작할 때 빈자리
2. 방장이 대기실에서 직접 추가한 자리
3. 게임 중 연결이 끊긴 사람의 자리 (임시로 대신 친다)
4. 게임 중 나간 사람의 자리

**동작 원칙**
- 봇은 서버 안에서 사람과 **같은 인터페이스**로 동작한다. 게임 진행기는 상대가 사람인지 봇인지 구분하지 않고 "출마해 달라", "카드를 내 달라"처럼 요청만 보낸다.
- 봇은 **자기 패와 공개된 정보만** 본다. 원작 AI(BSW, Xiao)는 바닥패를 몰래 보지만, 포팅할 때 이 부분을 뺀다.
- 사람이 따라갈 수 있도록 봇이 행동하기 전에 0.5~1초 정도 기다린다.
- 봇 이름은 원작의 좌석별 기본 이름(0번부터 아무개, 대중, 영삼, 태우, 두환, 정희)을 쓰고, 봇이라는 표시(🤖)를 붙인다.

**봇 수준 (단계적으로 개발)**

| 단계 | 내용 |
|---|---|
| 1차 (먼저 출시) | 규칙만 지키는 단순 봇. 공약은 패의 세기를 대략 평가해서 정하고, 카드는 낼 수 있는 것 중 간단한 기준으로 고른다. 원작 Ghost(무작위)보다 조금 나은 수준 |
| 2차 이후 (점차 개선) | Xiao 전략 포팅. 상대가 어떤 무늬를 가졌는지 확률로 추정하고, 누가 주공 편인지 추정해서 카드를 고른다 |

**끊김과 재접속**
- 연결이 끊기면 그 자리는 곧바로 봇이 이어받는다. 게임은 멈추지 않는다.
- 같은 토큰으로 다시 접속하면 다음 결정 시점부터 다시 사람이 조작한다.
- 끊긴 채 일정 시간(예: 5분)이 지나면 그 자리를 봇 자리로 바꾸고, 그 사람은 퇴장 처리한다.
- 방에 사람이 한 명도 남지 않으면 방을 닫는다. 봇끼리만 남은 방은 유지하지 않는다.

**차례 제한 시간**
- 방장이 방을 만들 때 정하고, 대기실에서 바꿀 수 있다. 게임 중에는 바꿀 수 없다.
- 선택지: 없음 / 30초 / 60초 / 90초 / 120초. 기본값은 60초로 한다 (30초는 너무 짧다는 피드백, 2026-10-18).
- **일시정지:** 자리에 앉은 사람(또는 방장)은 누구나 게임을 멈추고 다시 시작할 수 있다. 멈춘 동안 모든 차례 시간과 봇이 멈추고 행동을 받지 않으며, 다시 시작하면 남은 시간부터 이어 간다.
- 시간 안에 결정하지 않으면 봇 로직이 대신 결정한다. 끊김 처리와 같은 코드를 쓴다.
- 남은 시간은 모든 사람 화면에 보인다.

## 6. 서버 위치 추천

동시 접속이 적고 서버가 프로세스 하나라서 어디에 두어도 돌아간다. 다만 다음 두 가지를 고려해야 한다.
- 방 상태를 메모리에 두므로 **잠들지 않는 서버**여야 한다. 무료 플랜 중에는 일정 시간 접속이 없으면 서버가 잠들어 방이 사라지는 곳이 있다.
- WebSocket을 지원해야 한다.

| 단계 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **개발·첫 테스트 (추천)** | 내 PC에서 실행 + Cloudflare Tunnel | 무료. 바로 시작할 수 있고, 친구에게 https 주소를 줄 수 있음 | 내 PC가 켜져 있을 때만 접속 가능 |
| **상시 운영 (추천)** | Fly.io 같은 소형 컨테이너 호스팅에 Docker 이미지 배포 | 항상 켜져 있음. WebSocket 지원. 작은 인스턴스는 월 몇 달러 수준 | 카드 등록과 배포 설정이 필요함 |
| 대안 | 무료 VM (Oracle Cloud 무료 등)에 직접 설치 | 무료로 상시 운영 가능 | 서버 관리(보안 업데이트, https 설정)를 직접 해야 함 |
| 비추천 | 잠드는 무료 플랜 (Render 무료 등) | 무료 | 잠들면 진행 중인 방이 사라짐 |

**추천 경로**
1. 처음에는 내 PC와 Cloudflare Tunnel로 친구들과 테스트한다.
2. 계속 쓸 것 같으면 같은 Docker 이미지를 Fly.io에 배포한다.

코드는 어느 쪽에서도 똑같이 돌아가도록 만든다. 포트는 환경변수로 받고, 서버 하나가 정적 파일과 WebSocket을 함께 처리한다. 호스팅 가격과 무료 범위는 자주 바뀌므로 배포 직전에 다시 확인한다.

## 7. 통신 원칙 (상세 메시지 정의는 다음 단계에서 작성)

- WebSocket 위에서 JSON 메시지를 주고받는다.
- **클라이언트 → 서버: 의도만 보낸다.** 예: `bid`, `discard`, `play`, `chat`. 서버가 규칙 엔진으로 검사하고, 규칙에 어긋나면 거절한다.
- **서버 → 클라이언트: 받는 사람마다 다른 화면 상태를 보낸다.** 남의 패는 장수만 알려준다. 바닥패와 주공이 버린 카드는 주공에게만 보낸다.
- 재접속하면 서버가 현재 화면 상태 전체를 한 번 보낸다 (스냅샷). 그 뒤로는 변경 사항만 보낸다.
- 서버는 받은 메시지의 보낸 사람을 연결로 확인한다. 원작처럼 채팅 발신자를 꾸며낼 수 없다.

## 9. 남은 질문 (나중에 결정)

1. [그만]을 골라 자리를 비운 사람은 관전자로 남을까, 로비로 나갈까? (지금 초안: 본인이 선택)
2. 방장이 관전자를 내보낼 수 있게 할까?
3. 관전자 수에 제한을 둘까?
