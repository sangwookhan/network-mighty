# 아키텍처 리뷰

작성: 2026-10-18 (커밋 `18d28ef` 기준). 대상: `packages/engine`, `protocol`, `server`, `web` (약 6,600줄).
범위: 구조와 경계, 상태 관리, 게임 진행기, 통신, 봇, 보안, 성능, 운영·배포, 테스트, 프론트엔드 구조.

## 0. 요약

구조의 큰 방향은 맞다. 규칙은 순수 엔진으로 분리되어 서버와 화면이 함께 쓰고, 서버가 판정하며 각자 자기 패만 받는다.
게임 진행기는 원작 FSM 처럼 "요청 → 응답 대기" async 루프로 단순하고, 사람·봇·끊긴 사람을 같은 방식으로 다룬다.

바로 고쳐야 할 것은 두 가지다.
1. **봇 오류 하나가 서버 전체를 죽일 수 있다** (타이머 콜백 예외, 전역 처리 없음) — 모든 방이 사라진다.
2. **입력값 검증이 타입 선언에만 의존한다** (좌석 번호 등을 실제로 확인하지 않음).

그다음은 통신량(판당 사람마다 약 660KB), 봇이 게임 내부 전체를 읽을 수 있는 구조, 운영 준비(배포 이미지·로그·버전)다.

| 등급 | 수 | 의미 |
|---|---|---|
| 높음 | 2 | 서비스가 멈추거나 상태가 깨질 수 있음. 먼저 고친다 |
| 중간 | 7 | 지금 규모에서는 돌아가지만 사용성·유지보수·운영에 영향 |
| 낮음 | 6 | 개선하면 좋음 |

## 1. 현재 구조

```
engine (순수 TS, 의존성 없음)      규칙: 카드·덱·트릭·선거·프렌드·정산·프리셋·설명
   ↑
protocol (타입만)                   ClientMessage / ServerMessage / RoomView / GameView
   ↑                ↑
server (Node, ws)                   web (React, Vite)
 main.ts  HTTP+WS 한 포트            net.ts   WebSocket + 전역 상태(useSyncExternalStore)
 hub.ts   접속·로비·방(Room)          Lobby / Room / Board / panels / cards / cardArt / sound
 game.ts  한 판 진행기(Game)          style.css, fx.css
 bots     simple / smart (+ bench)
```

- 의존 방향이 한쪽으로만 흐른다 (engine ← protocol ← server/web). 엔진은 Node·브라우저 API 를 쓰지 않는다.
- 모든 상태는 서버 메모리에만 있다 (스펙 결정). 서버를 다시 시작하면 방이 사라진다.
- 서버는 상태가 바뀔 때마다 받는 사람별로 방 상태 전체(RoomView)를 보낸다. 클라이언트는 받은 것을 그대로 그린다.

### 잘 된 점

| 항목 | 내용 |
|---|---|
| 규칙 엔진 분리 | 순수 함수, 서버·화면 공용, 단위 테스트 123개 + 프리셋별 시뮬레이션 |
| 서버 판정 | 남의 패·바닥패는 해당 사람에게만. 요청 번호로 중복·지난 응답 무시 |
| 진행기 모델 | `ask(seat, 요청, 검증)` 하나로 사람·봇·시간 초과·끊김·넘겨받기·일시정지를 처리 |
| 통합 테스트 | 사람 3명 스크립트 클라이언트로 5개 프리셋 전체 진행, 재접속, 관전, 일시정지 등 14개 |
| 봇 평가 | 봇끼리 대결 실행기로 수치 비교·조정 가능 |

## 2. 발견 사항

### 높음

**H1. 봇 행동 중 예외가 나면 서버 프로세스가 종료된다**
- 위치: `game.ts` `botAct()` (타이머 콜백), 봇의 `throw new Error('no valid bid' / 'no valid final')`, `bot produced invalid action`
- 문제: 타이머 콜백에서 난 예외는 `game.run().catch` 로 잡히지 않는다. 서버에 `uncaughtException` 처리도 없다. 운영 모드에서 Node 가 죽고 **모든 방이 사라진다** (개발 모드는 자동 재시작).
- 제안: `botAct` 를 try/catch 로 감싸고, 봇이 실패하면 낼 수 있는 수 중 첫 번째로 대신 진행한다(로그 남김). 전역 `uncaughtException`/`unhandledRejection` 은 로그만 남기고, 문제가 된 방만 닫는다.

**H2. 클라이언트 입력값을 실제로 검증하지 않는다**
- 위치: `hub.ts` `sit` / `addBot` / `removeBot` (`this.seats[msg.seat]`), 그 밖의 메시지 필드
- 문제: TypeScript 타입은 실행 중에는 아무것도 막지 않는다. 좌석 번호에 `"__proto__"` 같은 값을 보내면 좌석 배열이 오염될 수 있다. 다른 필드도 형식 확인이 들쭉날쭉하다.
- 제안: 메시지마다 작은 검증 함수를 둔다 (좌석은 0..인원-1 정수, 문자열 길이, 열거값). 외부 라이브러리 없이 protocol 패키지에 둘 수 있다.

### 중간

**M1. 통신량: 판마다 사람당 약 660KB**
- 측정: 관전자 기준 한 판에 방 상태 메시지 약 73개 × 약 9KB. 대부분은 매번 같은 채팅 100줄, 규칙, 프리셋 설명이다.
- 영향: 집 서버 + 휴대폰 데이터·터널에서 느려지고 데이터를 쓴다. 5명이면 판당 서버가 3MB 이상 보낸다.
- 제안: 바뀌지 않는 정보(규칙·프리셋 설명)는 입장 때 한 번만, 채팅은 새 줄만 보내는 별도 메시지로. 게임 상태만 매번 보낸다 (먼저 이것만으로 대부분 줄어듦).

**M2. 봇이 게임 내부 전체에 접근한다**
- 위치: 봇은 `Game` 객체를 받아 `g.hands[...]` 등 모든 상태를 읽을 수 있다. 지금 코드는 자기 패만 읽지만, 막는 장치가 없다 (원작 BSW 가 바로 이 방식으로 치트였다).
- 제안: 봇에게도 사람과 같은 `GameView`(보는 사람별 화면 상태) + 요청만 준다. 그러면 공정성이 구조로 보장되고, 봇을 클라이언트처럼 테스트할 수 있다.

**M3. 남은 시간 표시가 기기 시계에 의존한다**
- 위치: 서버가 마감 시각(`deadline`, 서버 시계)을 보내고 화면이 자기 시계로 뺀다.
- 문제: 집 PC 서버와 휴대폰 시계가 몇 초 다르면 남은 시간이 틀리게 보인다.
- 제안: 남은 밀리초를 보내고, 받은 시점부터 화면에서 센다.

**M4. 프로토콜 버전 확인이 없다**
- 문제: 서버를 업데이트했는데 브라우저가 예전 화면을 들고 있으면 메시지 형식이 어긋나도 알 수 없다.
- 제안: `hello` 에 버전을 넣고, 다르면 "새로고침하세요" 안내.

**M5. 운영 준비 부족**
- 운영 실행이 `tsx` 로 TypeScript 를 그 자리에서 변환한다 (동작은 함). 배포 이미지(Dockerfile)·자동 재시작·로그가 없다. 로그는 `console` 세 군데뿐.
- 제안: 서버 빌드 단계 또는 Dockerfile, 프로세스 관리(systemd/pm2/컨테이너 재시작), 방 생성·종료·오류 정도의 구조화된 로그.

**M6. 화면 코드 구조: Board.tsx 667줄, CSS 덧씌우기**
- `Board.tsx` 하나에 23개 함수(배치, 애니메이션, 효과음, 공약 상자, 상태 표시줄, 내 패)가 있다.
- `style.css` 는 개선할 때마다 아래에 규칙을 덧붙여서 같은 선택자를 두 번 정의한 곳이 15군데다 (앞의 값이 뒤에서 덮어써짐).
- 제안: 기능별 파일로 나누고(좌석, 가운데 트릭, 내 패, 상자들), CSS 는 컴포넌트별 파일로 옮기면서 중복을 합친다. 동작 변경 없는 정리.

**M7. 남용 방지 장치가 없다**
- 채팅·방 만들기·닉네임 등록 횟수 제한, 같은 IP 접속 수 제한이 없다. 메시지 크기 제한(16KB)만 있다.
- 지인용이라 급하지 않지만, 인터넷에 주소를 공개하면 필요하다.
- 제안: 사람당 초당 메시지 수 제한(예: 채팅 1초 1회), 방 수 상한.

### 낮음

| 번호 | 내용 | 제안 |
|---|---|---|
| L1 | `hub.ts` 에 접속 관리(Hub)와 방(Room)이 함께 있음 (537줄) | `room.ts` 로 분리 |
| L2 | 웹 화면 테스트가 없음 (엔진·서버만 테스트) | 핵심 화면 흐름 e2e (브라우저 자동화 도구 설치 필요) |
| L3 | CI 가 없음 | GitHub Actions 로 테스트·타입 검사 |
| L4 | WebSocket Origin 확인 없음 | 토큰을 쿠키가 아니라 메시지로 보내서 위험은 낮음. 공개 시 Origin 허용 목록 |
| L5 | 서버 재시작 시 방 전부 소실 | 스펙 결정대로 유지. 업데이트 전 "곧 재시작" 공지 기능 정도 |
| L6 | 프리셋 보정이 `presetRules()` 안의 코드로 흩어짐 (노기·노프, 딜미스, 표준 5마 첫 공약) | 보정 목록을 표 형태 데이터로 모아 문서와 일치시키기 |

## 3. 제안하는 개선 순서

| 순서 | 항목 | 크기 | 비고 |
|---|---|---|---|
| 1 | H1 봇 예외로 서버가 죽지 않게 + 전역 예외 로그 | 작음 | 서버 재시작 필요 |
| 2 | H2 메시지 입력 검증 | 작음 | 통합 테스트에 잘못된 입력 추가 |
| 3 | M3 남은 시간을 밀리초로 | 작음 | 프로토콜 변경 |
| 4 | M4 프로토콜 버전 확인 | 작음 | 3번과 함께 |
| 5 | M1 통신량 줄이기 (채팅·고정 정보 분리) | 중간 | 프로토콜 변경 |
| 6 | M2 봇에게 GameView 만 주기 | 중간 | 봇 대결로 성능 변화 없는지 확인 |
| 7 | M6 화면 코드·CSS 정리 | 중간 | 동작 변경 없음, 화면으로 확인 |
| 8 | M5 배포·로그 (집 PC/NAS 운영 대비) | 중간 | Dockerfile 등 |
| 9 | M7, L1~L6 | 작음~중간 | 필요할 때 |

1~4는 작고 위험이 낮아 한 번에 할 수 있다. 5·6은 프로토콜과 봇 구조를 바꾸므로 각각 따로 커밋하고 테스트한다.
